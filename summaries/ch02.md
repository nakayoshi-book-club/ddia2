# 2章 非機能要件を定義する

> インターネットはあまりにもうまく作られたため、ほとんどの人は太平洋のような天然資源だと思っていて、人間が作ったものだとは思っていません。
> ― Alan Kay

『データ指向アプリケーションデザイン 第2版』2章（p.31–54）のサマリー。

## この章で言いたいこと

- **機能要件**（何ができるか）と同じくらい、**非機能要件**（速さ、信頼性、伸ばしやすさ、直しやすさ）が大事。遅すぎるアプリや壊れやすいアプリは、ないのと同じ
- 本章では4つの非機能要件を取り上げ、以降の章で使う用語を定義する

| 非機能要件 | 問い |
|---|---|
| パフォーマンス | 速さをどう定義し、どう測るか？ |
| 信頼性 | 何かが壊れても、正しく動き続けられるか？ |
| スケーラビリティ | 負荷が増えたら、リソースを足して対応できるか？ |
| メンテナンス性 | 長く運用し、変え続けられるか？ |

## 2.1 ケーススタディ：ソーシャルネットワークのホームタイムライン

X（旧Twitter）のようなSNSを想定する。

- 投稿は1日5億件、平均5,800件/秒（ピークは15万件/秒）
- 平均的なユーザーは200人をフォローし、200人にフォローされる。ただし分布は極端に偏っていて、フォロワーが1億人を超えるセレブもいる

### 読むときに集める（ポーリング）

users・posts・followsの3テーブルをJOINして、フォロー中のユーザーの最新1,000件を返すSQLを書ける。

- 5秒以内に投稿を届けたいので、クライアントが5秒ごとにクエリを投げる（**ポーリング**）
- 同時オンライン1,000万人 → 200万クエリ/秒
- 1クエリで200人分の投稿を引くので、**4億ルックアップ/秒**。数万人をフォローするユーザーには、さらに重い

### 書くときに配る（マテリアライゼーション）

- 投稿のたびに、フォロワー全員のホームタイムラインへ書き込む（メールボックスに配達するイメージ）。1つのリクエストが下流の複数のリクエストに広がることを **ファンアウト** と呼ぶ
- 5,800投稿/秒 × 200人 = **約116万書き込み/秒**。4億に比べて大幅に少ない
- 投稿が急増しても、配信はキューで遅らせてよい。読み込みはキャッシュを返すだけなので速いまま
- クエリ結果を事前に計算して更新し続けることを **マテリアライゼーション**、このキャッシュを **マテリアライズドビュー** と呼ぶ。**読み取りが速くなる代わりに、書き込みの仕事が増える**

### 極端なケース

| | 大量にフォローする人 | フォロワーが非常に多いセレブ |
|---|---|---|
| 問題 | タイムラインへの書き込みレートが高い | 1投稿で数百万〜1億回の書き込み |
| 対策 | 書き込みの一部を捨て、サンプルだけ見せる（どうせ全部は読まない） | 捨てられない。投稿を配らずに別に保存し、読み込みのときにマージする |

最適化しても、セレブを扱うには大量のインフラが要る。**設計を決めるのは平均ではなく分布の端**。

## 2.2 パフォーマンスの表現方法

- **レスポンスタイム**：リクエストを送ってから応答を受け取るまでの時間。ユーザーが最も気にする
- **スループット**：1秒あたりのリクエスト数やデータ量。必要なリソース、つまりコストを決める

スループットが処理の上限に近づくと、**キューイング** のせいでレスポンスタイムが急に悪化する（図2-3）。

### 過負荷から回復しないとき

遅延 → クライアントがタイムアウトして再送 → さらに過負荷（**リトライストーム**）。負荷が下がっても戻らない状態を **準安定障害**（metastable failure）と呼ぶ。

| どこで | 対策 |
|---|---|
| クライアント | 指数バックオフ（リトライの間隔を延ばし、ランダムにずらす） |
| クライアント | サーキットブレーカー、トークンバケット（エラーやタイムアウトを返した相手への送信を一時停止） |
| サーバー | 負荷の削減（load shedding：過負荷に近づいたら先回りして拒否） |
| サーバー | バックプレッシャー（クライアントに速度を落とさせる） |

### 2.2.1 レイテンシとレスポンスタイム

```mermaid
flowchart LR
  A[ネットワークレイテンシ<br/>行き] --> B[キューイング遅延] --> C[サービスタイム<br/>実際の処理] --> D[ネットワークレイテンシ<br/>帰り]
```

- **レスポンスタイム**：クライアントから見た全体の時間
- **サービスタイム**：サービスが実際にリクエストを処理している時間
- **キューイング遅延**：CPUが空くのを待つ時間など
- **レイテンシ**：リクエストが処理されずに潜伏している時間の総称

同じリクエストでも、コンテキストスイッチ、パケットの再送、GCの停止、ページフォールトなどでばらつく。少数の遅いリクエストが後続を待たせる **先頭ブロッキング** がばらつきの大部分を占めることが多く、キューイング遅延はサービスタイムに含まれないので、**レスポンスタイムはクライアント側で測る**。

### 2.2.2 平均値、中央値、パーセンタイル

- **平均**：スループットの限界を見積もるには使えるが、その遅さを実際に経験した人がどれだけいるかはわからない
- **中央値（p50）**：典型的な待ち時間
- **p95・p99・p999**：外れ値の深刻さ。高いパーセンタイルを **末尾遅延**（tail latency）と呼ぶ
- Amazonは内部サービスの要件をp99.9で決めている。最も遅いリクエストを受けるのは、データが多い（たくさん買ってきた）最も価値のある顧客だから。p99.99はコストに見合わないと判断した

レイテンシとユーザー行動の関係を示すデータは、意外と信頼できるものが少ない（Google、Bing、Akamai、Yahooの調査）。

### 2.2.3 レスポンスタイムメトリクスの活用

- **末尾遅延の増幅**：1つのリクエストで複数のバックエンドを呼ぶと、並列でも最も遅いものを待つ。1つでも遅ければ全体が遅く、呼ぶ数が増えるほど遅い呼び出しに当たる確率が上がる（例：10個がそれぞれ1%で遅いと、約10%のリクエストが遅くなる）
- **SLO**（目標。例：p50 < 200ms、p99 < 1秒、99.9%がエラーなし）と **SLA**（満たせなかったときの契約）
- パーセンタイルの **平均は数学的に無意味**。集約するときは **ヒストグラムを足し合わせる**（HdrHistogram、t-digest、OpenHistogram、DDSketch）

## 2.3 信頼性と耐障害性

信頼性とは、ざっくり言えば **何かがうまくいかなくても正しく動き続けること**。

- **障害（fault）**：システムの一部が正しく動かなくなること
- **機能不全（failure）**：システム全体が必要なサービスを提供できなくなること（SLOを満たせない）
- どちらと呼ぶかは見るレベルによる。ディスク1台の機能不全は、複数ディスクのシステムから見れば障害

### 2.3.1 耐障害性

- **耐障害性**：障害が起きてもサービスを提供し続けられること。耐えられるのは常に **特定の種類の障害を、特定の数まで**
- **単一障害点（SPOF）**：壊れるとシステム全体が機能不全になる部分
- タイムラインの例：ファンアウトの途中でマシンが落ちても、投稿を取りこぼさず重複もさせずに引き継ぐ（**厳密に1回のセマンティクス**、12章）
- **フォールトインジェクション**：わざと障害を起こして、耐障害性の仕組みを常にテストする。重大なバグの多くはエラー処理の不備にある。体系化したものが **カオスエンジニアリング**
- セキュリティ侵害のように回復できないものは、耐えるより予防する

### 2.3.2 ハードウェアとソフトウェアの障害

| ハードウェア | 頻度の目安 |
|---|---|
| HDD | 年2〜5%が故障。1万台なら毎日1台 |
| SSD | 年0.5〜1%。訂正不能なエラーは1台あたり年1回ほど |
| CPU | 約1,000台に1台が、まれに計算を誤る |
| メモリ | ECCでも年1%超のマシンで訂正不能なエラー |
| データセンター | 停電、設定ミス、火災・洪水・地震、太陽嵐 |

- **冗長化**（RAID、二重電源、バックアップ電源）で故障率を下げる。ただし効くのは障害が **独立** しているときだけで、実際には相関がある
- クラウドは1台の信頼性よりも、ソフトウェアでノード単位の障害に耐える方向に注力する（**アベイラビリティゾーン**）。1台ずつ再起動してパッチを当てる **逐次更新**（rolling upgrade）もできる

ソフトウェアの障害は全ノードが同じバグを持つので **強く相関** し、ハードウェアの障害より多くの機能不全を引き起こす。

- うるう秒でLinuxカーネルのバグが多数のJavaアプリを同時にハングさせた（2012年）
- 同じ型番のSSDが32,768時間の稼働で一斉に壊れるファームウェアのバグ
- 共有資源を食いつぶす暴走プロセス、依存先の遅延や破損した応答
- 単独のテストでは起きない **創発的動作**、**連鎖障害**

特効薬はない。前提とインタラクションを慎重に考える、徹底したテスト、プロセスの分離、クラッシュと再起動の許容、フィードバックループの回避、本番でのモニタリング。

### 2.3.3 人間と信頼性

- ある調査では、機能不全の主な原因はオペレーターの設定変更で、ハードウェアが関係したのは10〜25%
- いわゆる「ヒューマンエラー」は原因ではなく、**社会技術システムの問題の表れ**。人を責めるのは逆効果
- 技術的な対策：テスト（プロパティテストも）、すぐ戻せるロールバック、段階的なロールアウト、モニタリング、オブザーバビリティ、間違えにくいインターフェース
- 対策にはお金がかかり、組織は機能を優先しがち。問題は人ではなく **組織の優先順位**
- **責任追及をしない振り返り**（blameless postmortem）。「ボブはもっと注意すべきだった」も「Haskellで書き直そう」も、単純すぎる答え

**コラム「信頼性はどれほど重要か？」**：一時的な停止は許されても、データの喪失や破損は壊滅的。英国郵便局のHorizonスキャンダルでは、会計ソフトのバグで数百人が有罪判決を受けた。信頼性を犠牲にするなら、どこで手を抜いているかを自覚する。

## 2.4 スケーラビリティ

スケーラビリティは、負荷の増大に対処する能力。ただし **一次元のラベルではない**。

- この方向に成長したら、どんな選択肢があるか？
- リソースをどう足せばよいか？
- 今の成長の見込みだと、いつ今のアーキテクチャの限界に来るか？

ユーザーの少ないスタートアップでは、仮想的なスケールへの投資はむしろ柔軟さを奪う。

### 2.4.1 負荷を理解する

- まず今の負荷を数字で表す：リクエスト数/秒、1日に増えるデータ量、同時オンライン数のピーク、読み書きの比率、キャッシュのヒット率、ユーザーあたりのフォロワー数
- 「負荷を増やしたとき、リソースを変えなければ性能はどうなるか」「性能を保つにはリソースをどれだけ足せばよいか」
- **リニアスケーラビリティ**：2倍のリソースで2倍の負荷を同じ性能でさばける。実際にはコストが線形より速く増えることが多い

### 2.4.2 共有メモリ、共有ディスク、シェアードナッシング

| アーキテクチャ | 特徴 |
|---|---|
| 共有メモリ（**垂直スケーリング**、スケールアップ） | 強いマシンに移る。2倍のスペックは2倍を大きく超える費用で、ボトルネックのせいで2倍はさばけないことが多い |
| 共有ディスク（NAS・SAN） | CPUとメモリは別々でディスクを共有。競合とロックがスケールを制限する |
| シェアードナッシング（**水平スケーリング**、スケールアウト） | 各ノードが自分のCPU・メモリ・ディスクを持つ。リニアにスケールしうる、価格対性能比がよい、増減しやすい、耐障害性が高い。代わりに明示的なシャーディング（7章）と分散システムの複雑さ（9章） |

クラウドネイティブなDBの、ストレージとコンピュートの分離は共有ディスクに似ているが、DB専用のAPIでスケーラビリティの問題を避けている。

### 2.4.3 スケーラビリティの原則

- 汎用の「魔法のスケーリングソース」はない。1kB×10万件/秒と2GB×3件/分は、同じ100MB/秒でもまったく別の設計になる
- 負荷が **1桁増えるたびにアーキテクチャを見直す**。1桁より先を計画する価値は、ふつうない
- 互いにほぼ独立に動ける小さな部品に分ける（マイクロサービス、シャーディング、ストリーム処理、シェアードナッシング）
- 必要以上に複雑にしない。1台で済むならそれがよい。5サービスは50サービスよりシンプル

## 2.5 メンテナンス性

ソフトウェアのコストの大部分は、最初の開発ではなく継続的なメンテナンスにある。今日作るシステムも、長く生き残ればいつかレガシーになる。

### 2.5.1 運用性：運用を容易にする

- 「よい運用は不完全なソフトウェアを補えるが、よいソフトウェアも悪い運用のもとでは信頼性高く動けない」
- 大規模では自動化が必須。ただし **自動化は諸刃の剣**：自動化できないまれなケースほど複雑で、扱う人には高いスキルが要る。自動化が誤動作すると原因を追いにくい
- データシステムができること：モニタリングとオブザーバビリティ、1台のマシンに頼らない、わかりやすいドキュメントと運用モデル、適切なデフォルトと上書きの自由、自己回復と手で制御する余地、予測できる振る舞い

### 2.5.2 簡潔性：複雑さを管理する

- 複雑さに絡め取られたプロジェクトは **大きな泥だんご**（big ball of mud）
- **本質的な複雑さ**（問題領域に固有）と **偶発的な複雑さ**（ツールの制約に由来）。ただし境界はツールの進化で動く
- 最良の道具は **抽象化**。高水準言語はマシンコードを、SQLはディスク上のデータ構造・並行性・クラッシュ後の不整合を隠す

### 2.5.3 発展性：変更を容易にする

- 要件は変わり続ける。疎結合でシンプルなシステムほど変えやすい
- 変更を難しくする主な要因は **不可逆性**。移行先に問題が出たとき古いDBに戻せないと、リスクはずっと高い

---

## まとめ

1. **パフォーマンス**：レスポンスタイムは分布で見る。パーセンタイルとSLO・SLA
2. **スケーラビリティ**：負荷が増えても性能を保つこと。独立に動く小さな部品に分ける
3. **信頼性**：耐障害性で、部品が壊れても動き続ける。ソフトウェアの障害は相関が強い。人のミスには、責任追及をしない振り返り
4. **メンテナンス性**：運用性・簡潔性・発展性。よく理解された部品と有用な抽象化で組み立てる
